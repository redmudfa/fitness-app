## 一、小程序 vs Web 应用：选型分析

### 结论：选 **Web 应用（PWA）**

### 理由

| 维度 | 微信小程序 | Web (PWA) |
|------|-----------|-----------|
| 审核机制 | 需要提交微信审核，个人主体审核周期 1-7 天 | 无需审核，迭代即上线 |
| 开发效率 | 必须使用微信开发者工具，受 WXML/WXSS 限制 | 标准 React/TS/H5 开发，工具链成熟 |
| 设备兼容 | 仅微信内运行 | 任何浏览器，手机/平板/PC 均可 |
| 离线能力 | 有限 | Service Worker 支持完整离线 |
| 安装体验 | 微信内即用 | 可添加到主屏幕，接近原生体验 |
| GPS/传感器 | 部分 API 受限 | Web API 完全可用（Geolocation 等） |
| 生态锁定 | 强依赖微信 | 无锁定，将来可迁移 |
| 成本 | 免费，但需微信认证（个人 30 元/年） | 仅服务器成本 |

**核心判断**：自用 App 没有多用户分发需求，审核流程完全是负收益。Web + PWA 在迭代速度、设备兼容、技术自由度上全面领先。唯一牺牲的是微信内的社交分享——但对自用 App 来说这无关紧要。

## 三、技术选型与架构

### 3.1 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 前端框架 | React 18 + TypeScript | 已确定，生态最成熟 |
| 构建工具 | Vite | 开发体验极佳，HMR 快 |
| UI 框架 | Tailwind CSS + shadcn/ui | 轻量、可定制、移动端友好 |
| 路由 | React Router v6 | 标准方案 |
| 状态管理 | Zustand | 比 Redux 轻，适合中小应用 |
| 图表 | Recharts | React 原生，够用 |
| 后端运行时 | Node.js | 已确定 |
| 后端框架 | Express / Fastify | 轻量 REST API |
| ORM | Drizzle / Prisma | 类型安全，SQLite 支持好 |
| 数据库 | SQLite (better-sqlite3) | 单用户场景最优：零配置、无运维 |
| PWA | vite-plugin-pwa | 添加到主屏幕、离线缓存 |
| 部署 | VPS（如 1核1G 轻量云） | 自用场景足够 |

## 五、设计原则

1. **离线优先**：所有核心功能不依赖网络，数据本地优先，网络同步为辅助
2. **极简录入**：训练中的交互尽可能少——大按钮、预设值、一键完成
3. **数据安全**：SQLite 文件纳入备份策略，支持导出以防数据丢失
4. **移动端优先**：UI 以手机竖屏为第一设计目标，PC 仅作为补充
5. **渐进增强**：先跑通核心闭环（录入→查看），再叠加分析/可视化

## 六、附录：技术决策 FAQ

**Q: 为什么用 SQLite 而不是 MySQL/PostgreSQL？**
A: 单用户场景，没有并发读写，没有分布式需求。SQLite 零配置、零运维、备份就是一个文件复制。够用且优雅。

**Q: 为什么不用 React Native 直接做 App？**
A: 自用场景下 Web + PWA 体验已足够好，RN 会增加开发和维护成本。如果 PWA 体验确实不够，Phase 5 再迁移也不迟——此时已有完整的 API 和业务逻辑，只需换一个前端壳。

**Q: 后端是否有存在的必要？能不能纯前端？**
A: 纯前端（localStorage/IndexedDB）可以实现，但换设备、清缓存会导致数据丢失。有后端 + SQLite 的好处是数据持久化和备份更可靠。后端也可以部署在本地（localhost），不依赖外网。
